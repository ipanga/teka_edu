# Alwaysdata PROD deployment and audit policy

This release implements the owner's narrow A + C direction for review. It authorizes no hosted
permission change, initialization or deployment. Provider clarification and separate execution
approval remain required. Staging behavior and the frozen 46 migrations are unchanged.

## Distinct accounts and scope

- `congofoot_user_teka_edu_prod` is the deployment/read-write login. READ ONLY inspection
  transactions do not convert it into the audit account.
- `congofoot_readonly_user_teka_edu_prod` is the dedicated audit login. Its confirmed global
  defaults are SELECT on future deployment-created tables and EXECUTE on future functions.
  These match the documented preset, but provider creation/regeneration provenance is unproved.

PROD access verification permits this exact audit recipient only for table-level SELECT without
any grant option on the 36 source-hash-checked canonical ordinary tables owned by the deployment
login. It is not a general accepted-recipient exception. Unknown tables, other recipients,
column grants, write/REFERENCES/TRIGGER rights and grant options remain rejected. Effective table
and column rights are checked, so PUBLIC and inherited rights cannot turn SELECT into writes.
The audit role must exist, be a non-elevated LOGIN, have no role memberships or application
ownership, no database/schema CREATE, no non-public application schema USAGE, and no DEV CONNECT.
This deliberately rejects even unreviewed non-elevated membership; changing that requires review.

RLS remains enabled with no policies. SELECT grants do not provide RLS bypass or complete data
visibility. Zero visible rows cannot establish empty tables. No new policy, BYPASSRLS, owner
membership or FORCE RLS change is introduced. The eight-field genuine-boolean result contract,
NULL safety and sanitized rejected-field diagnostics remain unchanged.

## Initialization-only object restrictions

After the transaction lock, identity and empty baseline guards, frozen migration execution, and
exact application source-shape/body validation, PROD initialization alone:

1. Rechecks the audit role profile, current object ownership, exact routine signatures, and an
   assigned open write transaction.
2. Removes audit EXECUTE from only `private.check_dated_row_within_school_year()` and
   `private.check_school_year_contains_dated_rows()`.
3. Removes audit table privileges on only `teka_migrations.history`: consultation of history
   has not been approved. History table and column ACLs to unapproved recipients are rejected.

These are additional tooling steps within the guarded initialization transaction, before all
pre-COMMIT schema/data/history/access/integrity gates. No frozen SQL file changes. No global
ALTER DEFAULT PRIVILEGES, role creation, GRANT, CASCADE, retry, reset or repair is performed.
The functions are invoker-security trigger routines; EXECUTE is unnecessary for the metadata
audit. Existing SECURITY DEFINER and exact routine shape/body checks remain mandatory. Effective
audit EXECUTE on public/private application routines is also explicitly denied.

Cleanup refuses missing/malformed guards or unexpected owners. Only exact newly initialized
PROD invokes it. Managed verification and subsequent apply do not silently repair grants.
Any error retains the existing transactional ROLLBACK behavior; COMMIT acknowledgement and the
existing timeouts/watchdog remain unchanged.

## Global defaults and future objects

Provider defaults remain intact. Future deployment-created functions/history tables can inherit
these rights again, including after a UI/API permission save. The validator rejects drift; it
never automatically re-runs cleanup during verification. New migrations/objects need a reviewed
object policy, not automatic expansion of the canonical registry or routine cleanup list. An
unapproved history column grant is rejected rather than silently removed. Saving provider
permissions may reset custom SQL ACLs: actual maintenance behavior requires Alwaysdata confirmation.

## Validation and remaining approval boundary

The required isolated PG16 replay now includes the real validator and restrictions, source-bound
SELECT success, all denied table privileges, grant options, column/PUBLIC rights, unapproved
recipients, inherited future grants, history ACLs, ownership/membership/elevated-role/DEV/schema
negatives, and rollback restoration. Tests run only in the isolated local replay database; no
hosted login or DEV session is accepted. Unit tests cover malformed cleanup guards and the
unchanged eight-field parser; staging SQL does not contain the PROD exception.

CI/replay evidence must bind the exact reviewed release/tooling before owner approval. Synthetic
fixtures prove mechanisms, not provider persistence or current live role-profile success.
Historical operation 96 remains unproved. Historical backup/recovery evidence and the accepted
limitation that a real backup restore is untested remain unchanged. PROD initialization and
application deployment remain NO-GO until their separate approvals.
