# Environment Setup

This guide takes the project owner step by step through configuring every environment. You do not need to have written the code to follow it.

- What each variable means: [ENVIRONMENT_VARIABLES.md](ENVIRONMENT_VARIABLES.md), the authoritative inventory.
- How deployments run: [DEPLOYMENT.md](DEPLOYMENT.md).

**Rules while following this guide**

- Never paste a real key, token or password into a file in this repository, into an issue, or into chat. Values go only into Vercel, GitHub secrets or your password manager.
- Keep DEV and PROD values separate. A staging or local setup that reaches the PROD database is a high-severity defect.
- Never change the PROD database schema from the Supabase dashboard. Schema changes are migrations only (ADR-017).

## 1. Local environment

No cloud account, credential or environment file is needed.

```bash
npm ci                                   # install exact dependency versions
npx playwright install chromium          # browser for E2E tests (once)
npm run dev                              # http://localhost:3000, with built-in defaults
```

**Optional: `.env.local`.** The repository deliberately contains **no** `.env*` file, not even a template (ADR-023). To override a default, create the file yourself:

```bash
touch .env.local        # Git-ignored: never commit it
```

Then add only the variables you need, using the "Local: `.env.local`" example in [ENVIRONMENT_VARIABLES.md](ENVIRONMENT_VARIABLES.md#local-envlocal-optional) as a guide.

**Optional: local Supabase.** The app does not need it yet, because child progress is stored locally in V1.

```bash
npm run db:start      # first run downloads the Supabase images (several minutes)
npx supabase status   # prints Project URL, Publishable key, Secret key, Database URL, Studio URL
```

To fill `.env.local`, either copy the printed values into it by hand, or print them already named for this project and paste the lines into `.env.local`:

```bash
npx supabase status -o env \
  --override-name api.url=NEXT_PUBLIC_SUPABASE_URL \
  --override-name auth.publishable_key=NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY \
  --override-name auth.secret_key=SUPABASE_SECRET_KEY \
  --override-name db.url=DATABASE_URL
```

- Use the `DATABASE_URL` value for `DIRECT_DATABASE_URL` too.
- The local keys are generated by your local stack and are not shared credentials, but still keep `.env.local` out of Git (it is ignored).
- Supabase Studio runs at http://127.0.0.1:54323.
- Stop the stack with `npm run db:stop`.

**Verify local:**

- [ ] `npm run verify` passes (format, lint, typecheck, unit tests, content validation, build)
- [ ] `npm run test:e2e` passes (after `npm run build`)
- [ ] `npm run docker:build && npm run docker:smoke` passes
- [ ] `npm run db:start && npm run db:test` passes

Project refs and URLs are public identifiers, not secrets (they are also in `lib/env/supabase-projects.ts` for the environment guard).

**Where the secret values are.** On the owner's Mac, they are in the **macOS login Keychain**: one generic-password item per value, with the project name as the account and the variable name as the service. They were fetched directly from Supabase (dashboard **Connect** / **API Keys** equivalents) and are never written to files or chat:

| Keychain service                                  | Content                                                                              |
| ------------------------------------------------- | ------------------------------------------------------------------------------------ |
| `supabase-db-password`                            | database password (`SUPABASE_DB_PASSWORD`)                                           |
| `SUPABASE_PROJECT_ID`, `NEXT_PUBLIC_SUPABASE_URL` | project ref / URL                                                                    |
| `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`            | `sb_publishable_…`                                                                   |
| `SUPABASE_SECRET_KEY`                             | `sb_secret_…`                                                                        |
| `DATABASE_URL`                                    | transaction pooler, `aws-1-eu-west-3.pooler.supabase.com:6543` (serverless / Vercel) |
| `DIRECT_DATABASE_URL`                             | direct `db.<ref>.supabase.co:5432`, **IPv6 only** (see below)                        |

To read one without displaying it, pipe it into the next tool, for example `security find-generic-password -a teka-edu-dev -s DATABASE_URL -w | pbcopy`. Keep a copy in your password manager if you want a second place. The values can also be re-read at any time from the Supabase dashboard (API Keys, Connect), or with `npx supabase projects api-keys --project-ref <ref> --reveal`.

Notes:

- **Legacy keys:** both projects still have the legacy JWT `anon` / `service_role` keys. Nothing uses them. Optionally disable them under Settings → API Keys → Legacy API keys, once you have confirmed nothing depends on them.
- **Direct connection:** `DIRECT_DATABASE_URL` resolves to IPv6 only. It is unreachable from IPv4-only networks, including this Mac's network (tested 2026-09-11) and Vercel. Use the pooler URLs. For direct-style tooling over IPv4, use the **session pooler** (same pooler host, port 5432). The CLI and CI already connect through the pooler.
- **Free plan limits:** an inactive project is **paused after about a week** (restore it from the dashboard), and there are **no downloadable backups or point-in-time recovery**. Before real child data lands in PROD, upgrade PROD or schedule `supabase db dump` exports ([DEPLOYMENT.md](DEPLOYMENT.md#database-rollback-and-recovery)).
- **Local CLI link:** this working copy is linked to **DEV** (`npx supabase link --project-ref quyhkkizsmosybavoewd`, state in the ignored `supabase/.temp/`). Never link a working copy to PROD. PROD is reached only by CI, or by explicit read-only commands with `--project-ref`.
- **Schema changes:** leave the schema alone. CI applies `supabase/migrations/` (ADR-017).

## 13. Verification procedure

1. [ ] **CI:** open a PR into `develop`. All CI jobs are green.
2. [ ] **Staging:** merge into `develop` (or run "Deploy staging" manually), then check:
   - the run log shows `supabase migration list` / `db push` against the DEV ref (never PROD)
   - the job summary shows the deployment URL
   - `https://<staging-url>/api/health` returns `"status":"ok"`, `"environment":"staging"` and the commit SHA
   - the smoke tests are green
3. [ ] **Production:** open a PR `develop → main` and merge it. Check the same points as for staging, with `"environment":"production"` and the PROD ref.
4. [ ] **Isolation:** in the Vercel Preview variables, confirm no value contains the PROD project ref. After section 5, the app enforces this.
5. [ ] **Rollback drill (optional):** on staging, practise `vercel rollback` as described in [DEPLOYMENT.md](DEPLOYMENT.md#application-rollback).
